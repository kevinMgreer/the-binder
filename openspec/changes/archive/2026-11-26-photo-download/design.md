## Context

The full-size view is a `Sheet` with `hideTitle` (`src/app/Sheet.tsx`): a dark backdrop, the photo, an icon-only X (`.viewer-close`) absolutely placed at the top right, and two small Front/Back dots when both photos exist. `CardDetail.tsx` renders `<PhotoView key={viewing} card side>` inside it. `PhotoView` loads the thumb and the full blob for its side from `photos` (the `PhotoStore` port) and, when the full photo is missing and the phone is online, downloads it with `remote.downloadPhoto(fileId)` and caches it with `photos.cacheFull`. Offline without a full photo it shows the thumbnail and "Full photo will load when online". Drive file names come from `photoFileName(card, side)` in `src/sync/names.ts`. Capacitor is 8.6; the app's `minSdkVersion` is 24 (Android 7).

## Decisions

- **Plugin: `@capacitor-community/media` 9.x.** Version 9 is the line maintained for Capacitor 8 (9.1.0, published 2026-11-23, peer `@capacitor/core >=8.0.0`). It is one Java file on Android, and its manifest declares no permission. `savePhoto({ path, albumIdentifier, fileName })` takes a `data:` URL; the extension comes from the MIME type, so `image/webp` saves as `.webp`. Outside its opt-in "gallery mode" it asks for no permission on any Android version, 7 to 16. It writes into the app's own media folder (`getExternalMediaDirs()[0]/The Binder`, i.e. `Android/media/<app id>/The Binder/`) and asks the media scanner to index the file, so Gallery and Google Photos list it as a "The Binder" folder. So no permission prompt on Android 10+, and none on 7 to 9 either.
  Alternatives:
  - `@capacitor/filesystem` 8.1.5. Rejected: it has no media scan, so Gallery would not see the file. Writing to a public Pictures folder needs `WRITE_EXTERNAL_STORAGE` and a prompt on Android 9 and older, and on Android 11+ it is limited by scoped storage.
  - A local plugin in `android/app` that inserts into `MediaStore.Images` with `RELATIVE_PATH = "Pictures/The Binder"`. This is real MediaStore, and the file survives an uninstall. It needs no permission on Android 10+ but needs `WRITE_EXTERNAL_STORAGE` (`maxSdkVersion="28"`) and a runtime prompt on Android 7 to 9, and it adds about 50 lines of Java we maintain. Rejected for now; it is the fallback if open question 1 goes that way.
  - The share sheet (`@capacitor/share`). Rejected: ruling T-58 says straight to the gallery, and the brief skips sharing.

  Cost stays at $0: the plugin is open source (MIT) and nothing calls a service except the existing Drive download.
- **Port: `Gallery { save(photo: Blob, name: string): Promise<void> }`** in `src/ports/index.ts`, added to `Ports` as `gallery`. `FakeGallery` in `src/adapters/fakes.ts` records `{ photo, name }` in `saved` and throws `error` when set, like `FakeReleaseFeed`. `createFakePorts()` returns it. `main.tsx` sets `ports.gallery = new CapacitorGallery()` inside the existing `Capacitor.isNativePlatform()` block. The browser dev and e2e builds keep the fake, because the plugin has no web side. Alternative: call the plugin straight from `PhotoView`. Rejected: the tests could not run without it, and every other native call goes through a port.
- **Adapter `src/adapters/capacitor-gallery.ts`.** It turns the blob into a data URL (`FileReader.readAsDataURL`) and reads `Media.getAlbumsPath()`. Then it calls `Media.createAlbum({ name: "The Binder" })` and ignores its rejection, because the plugin rejects "Album already exists" on every save after the first. A real failure to create the album still comes out of the next call. Last it calls `Media.savePhoto({ path: dataUrl, albumIdentifier: \`${albumsPath}/The Binder\`, fileName: name })`. It uses `getAlbumsPath` rather than `getAlbums()`, which queries the whole MediaStore and matches by name. No unit test: it is straight-line glue, checked by the compile and the phone task.
- **Name: reuse `photoFileName(card, side)` without the `.webp`**, for example `2024-topps-1-shohei-ohtani-front-1a2b3c4d`. It is the same name as the Drive file, so the two match, and `photoFileName` already handles accents and empty fields. The plugin writes with a plain `FileOutputStream`, so saving the same side again replaces the file and leaves no duplicate. Alternative: a spaced name like `2024 Topps 1 Ohtani front`. Rejected: a second naming rule for the same file.
- **Format: the stored WebP as is.** Android's Gallery and Google Photos show WebP. Alternative: re-encode to JPEG through a canvas. Rejected: more code and a second lossy pass, for no gain on Android.
- **The button lives in `PhotoView`, not in `Sheet` or `CardDetail`.** `PhotoView` already owns the full blob and the fetch-and-cache path. The fetch moves out of the effect into a local `loadFull()` that both the effect and the save handler call, so the save reuses it and never touches the thumbnail. The button is `<button className="icon-button viewer-close viewer-save" aria-label="Save to phone">` with `<Icon name="download" />`. CSS places it absolutely at the same top as the X, one 48 px slot plus a small gap to its left. While a save runs it is disabled, so a double tap saves once. `CardDetail.tsx` needs no change. Alternative: an `action` slot in `Sheet`'s head row. Rejected: the handler needs `PhotoView`'s blobs, so state would have to move up to `CardDetail`.
- **Save flow.** `full = blobs.full ?? (online && ref.fileId ? await loadFull() : undefined)`. With no full photo it saves nothing and shows "Connect to the internet to save the full photo". Otherwise it calls `gallery.save(full, photoFileName(card, side).replace(/\.webp$/, ""))` and shows "Saved to Photos". A failed download or save shows "Could not save the photo". The message is a `<p role="status" className="viewer-toast">` over the bottom of the photo, above the dots, in viewer colours, cleared after 3 s with a timer that is cleared on unmount. It is never a new row in the layout.
- **Icon:** add `download` to `PATHS` in `src/app/Icon.tsx`, using the Material "file download" path (`M19 9h-4V3H9v6H5l7 7 7-7zM5 18v2h14v-2H5z`) to match the existing set.

## Risks

- The files sit in the app's own media folder, so Android will probably delete them when the app is uninstalled (not on an update). See open question 1.
- The plugin indexes the file with the old `ACTION_MEDIA_SCANNER_SCAN_FILE` broadcast, deprecated since Android 10. Android still indexes the app's media folder, but the photo may take a moment to show in Google Photos. The phone task checks this.
- `.viewer-save` must not cover the photo's top-right corner more than the X already does. The design e2e test (`e2e/design.spec.ts`) and the phone check cover this.
- jsdom has `FileReader`, but the adapter is not unit tested, so a wrong data URL shows up only on the phone.

## Open questions

1. Does a saved photo vanish when the app is uninstalled (as opposed to updated)? If the owner reinstalls by uninstalling first, the saved photos would go too. If that matters, switch the adapter to the local MediaStore plugin (alternative above), which costs a storage prompt on Android 7 to 9. The phone task checks whether the photo survives an update install.
2. Should the toast say "Saved to Photos" when Google Photos is not the gallery app? Kept as the brief words it.
